## Context

`supervisor/config.json` already carries a `dbNodes` section (`KV1`, `KV2`, both `storage: ["*:*"]`) but nothing consumes it — `lib/masterfree/config.ts` has no accessor. The nearest precedent is `eventNodes`/`shards`: `Config.getEventNodes()`, `Config.findShardsForNode(nodeId)`, `Config.validateShardsForNode(nodeId)`, consumed by `bin/masterfree/ndb.ts` at startup to determine which `KEEP_ADVANCE_HISTORY.<shardTag>` topics a storage node subscribes to (see `add-distributed-message-sharding`, fully implemented, not yet archived).

Today, KV/admin logic runs in two places:
- `lib/mono/onedbrouter.ts` (`OneDbRouter`): `AdminApiServer` is constructed per-realm inside `router.createRealm(realmName)`, lazily, the first time a realm is touched. This is the only place `AdminApiServer` is wired up at all.
- `bin/masterfree/ndb.ts`: `ProjectionListener` and `SqliteKvFabric` are already constructed alongside `EventStorageTask`/`StageTwoTask`, sharing the same `DbFactory`/db handle and node process — but `AdminApiServer` is **not** wired in here (confirmed gap, not yet built).

`EventStorageTask.commit_segment` already does two things after a segment commits: it emits `SEGMENT_COMMITTED` in-process on `dbFactory` (consumed today by the co-located `ProjectionListener`), and it separately publishes `Event.SEGMENT_COMMITTED` over HyperNet into the sys realm via `this.api.publish(...)`, which is already piped live-tail to every attached entry node (`storageTask.listenEntry`). The wire path already exists; only a subscriber on the KV-node side is new.

See `openspec/specs/distributed-mode.md` for the full lifecycle and the stateless-voting invariants this proposal must not disturb, and `openspec/specs/kv-storage-registry/spec.md` for the projection lifecycle (`inactive → refreshing → online/failed`) this proposal does not change.

## Goals / Non-Goals

**Goals:**
- Give `Config` a first-class, tested accessor surface for `dbNodes`, symmetric with the existing `eventNodes` surface.
- Define the `<realm>:<key-pattern>` grammar precisely enough that `kv-node` can implement matching against it without inventing a second pattern language.
- Establish, as a documented contract, that KV-node instances are stateless-w.r.t.-voting, redundant-tolerant consumers — so the eventual dedicated process can be implemented without re-litigating cluster-topology questions.
- Identify, explicitly, the parts of the KV-node split this proposal does *not* settle, so `kv-node`'s implementation change knows what it still owns.

**Non-Goals:**
- Building `bin/masterfree/kvnode.ts` or moving `AdminApiServer`/`ProjectionListener`/`SqliteKvFabric` construction out of `OneDbRouter`/`ndb.ts`.
- Changing `lib/masterfree/hyper.h.ts`, `EventStorageTask`, or the StageOne/StageTwo protocol in any way.
- Solving realm-discovery for wildcard (`*`) realm storage patterns (see Open Questions) — this proposal defines what "covered" means, not how a not-yet-instantiated realm's admin surface gets registered.
- Sharding or filtering the `SEGMENT_COMMITTED` broadcast itself at the publisher (storage-node) side. It stays a broadcast to every attached entry, exactly as today; a KV-node filters client-side, the same way `ProjectionListener.handleSegmentCommitted`'s `forEachRealm` + per-projection `uriPattern` check already filters today.

## Decisions

### 1. Config accessors mirror `eventNodes` exactly
`getDbNodes()`, `getDbNodeById(nodeId)`, `findStoragePatternsForNode(nodeId): string[]`, `validateStorageForNode(nodeId): void`. Rationale: this is the second cluster-topology config section after `eventNodes`; reusing its exact shape and naming keeps `config.ts` predictable and lets `validateStorageForNode` follow the same fail-fast-at-startup convention already used in `bin/masterfree/ndb.ts` (`config.validateShardsForNode(conf_node_id)` called before the node starts serving).

Alternative considered: a single generic `getNodesOfType(type)` accessor. Rejected — `eventNodes` and `dbNodes` have different per-entry shapes (`shards: number[]` vs `storage: string[]`) and different validation rules; a generic accessor would need to be typed as `any` at the call site anyway, losing the benefit.

**kv-node verification:** Checked against the actual `Config` class (`lib/masterfree/config.ts`) — there is no existing `getEventNodeById` to mirror at all; `eventNodes` only exposes `getEventNodes()` (whole map) and `findShardsForNode()` (silently returns `[]` on a miss). The closest "resolve one id, throw if missing" precedents are `getSyncById`/`getGateById`. `getDbNodeById` should follow *that* throwing convention rather than eventNodes' silent-`[]` style, since a missing id there is a startup misconfiguration (e.g. a KV-node reading its own entry by `NODE_ID`, mirroring `config.validateShardsForNode(conf_node_id)` in `ndb.ts`), not an expected empty case. `tasks.md` task 1.2 already specifies the throwing behavior — this note just aligns the prose above with it.

### 2. Pattern grammar: split-on-first-`:`, reuse `topic_pattern.ts`
`<realm>:<key-pattern>` splits on the *first* `:` only (a key-pattern segment itself may validly be a single dotted token with no `:`, since FOX topics never contain `:`; this rules out ambiguity without needing an escape syntax). Realm is `*` or an exact name — not a topic pattern; there is exactly one flat namespace of realm names and no established sub-realm hierarchy to pattern-match against, so a topic-style wildcard (`app.*`) does not apply. `key-pattern` reuses `defaultParse()`/`match()` from `lib/topic_pattern.ts` verbatim — the same functions already used by `KvProjection.applyEvent` to compare a committed event's URI against a projection's `uri_pattern`, and by `AdminApiServer`'s schema `urlPattern`. This keeps exactly one pattern-matching implementation in the codebase for this concept, avoiding subtly different wildcard semantics between "does this event match a projection" and "does this projection fall inside a node's declared responsibility."

Alternative considered: a full glob syntax over `realm.key.path` as one combined dotted string (no `:` separator, realm is just the first path segment). Rejected — realms and topics are already validated/typed as separate concepts everywhere else in the codebase (`BaseRealm`, `realmName` columns, `storage_desc_${realmName}` table naming); collapsing them into one path would require every consumer to special-case "first segment is actually the realm," which is more error-prone than a single `:` split.

**kv-node correction:** Reusing `match()`/`defaultParse()` verbatim also inherits its exact wildcard semantics, and those don't say what the checked-in example implies. In `lib/topic_pattern.ts`, `match()` requires equal parsed length unless the filter uses `#`: `*` matches exactly *one* segment, only `#` matches a variable-length (including multi-segment) suffix. That means the checked-in `supervisor/config.json` example — `"storage": ["*:*"]` for both `KV1` and `KV2` — does **not** cover multi-segment topics like `orders.created` under this reused matcher; key-pattern `*` only covers single-token topics such as `orders`. A pattern meaning "every key, any depth" must be written `*:#`, not `*:*`. This is worth fixing before anyone treats the checked-in example as a template: recommend correcting `supervisor/config.json`'s `dbNodes.storage` example to `"*:#"`, and stating the `*` vs `#` distinction explicitly in the grammar description in the spec delta so `kv-node` doesn't inherit a silently-broken "match everything" default. See `tasks.md` 2.3 (added).

### 3. Overlap = independent redundancy, no coordination
Directly reuses the `eventNodes.shards` precedent (DB1:[0,1,2,3] / DB2:[2,3,4,5] already overlap in the checked-in config, and `EventStorageTask` instances for different `advanceOwner`s already run fully independently against their own `DbFactory`). A KV-node is single-writer only to its *own* SQLite file; two KV-nodes with overlapping `storage` patterns each maintain their own copy, and nothing in `kv-storage-registry`'s activation/replay logic (idempotent, ordered by committed `eventId` string, `INSERT OR REPLACE` semantics) requires them to agree. This is what makes the "no leader election" claim safe rather than aspirational.

Alternative considered: treat overlapping patterns as a config error requiring disjoint partitioning (an actual shard map, like `eventNodes.shards`). Rejected for this proposal — the checked-in example config already has two nodes both declaring `"*:*"`, which reads as intentional full replication for HA/read-scaling, not a mistake to reject. Partition-style disjoint ownership remains expressible (patterns simply don't overlap); this design does not forbid it, it just doesn't require it.

**kv-node verification:** Confirmed against `supervisor/config.json` — `DB1: [0,1,2,3]` and `DB2: [2,3,4,5]` genuinely overlap on shards `2` and `3`, and each `EventStorageTask` instance really does own its own `DbFactory`/SQLite file independently. The precedent is real, not asserted. No change needed here.

### 4. Reuse the existing `SEGMENT_COMMITTED` wire broadcast; no new event
Confirmed by reading `lib/masterfree/storage.ts`, with one correction to how this was first described: the wire publish is not inside `commit_segment` itself — `commit_segment` only computes and returns the `CommittedSegmentEvent` result. The publish lives in the constructor's `Event.ADVANCE_SEGMENT_RESOLVED` subscribe handler, immediately after awaiting `commit_segment(...)`:
```
this.commit_segment(...).then((result) => {
  this.dbFactory.emit(SEGMENT_COMMITTED, result)                 // always fires (in-process)
  if (result.events.length > 0) {
    this.api.publish(Event.SEGMENT_COMMITTED, result, { exclude_me: false })  // conditional (wire)
  }
})
```
This matters for the fan-out question below: the in-process `dbFactory.emit` (consumed by a co-located `ProjectionListener`) fires on *every* resolved segment, including ones where this node's `bufferToWrite` had no data for that `advanceOwner:advanceStamp` key (`result.events` empty — e.g. an advance cycle that only touched shards owned by a different storage node). The wire publish is skipped in that empty case. A wire-fed KV-node therefore already receives a node-local reduction in traffic (it never sees a node's empty commits at all) that a co-located `ProjectionListener` does not benefit from — though it also means a wire-fed KV-node's `advancePosition` for a realm never gets nudged forward on those empty commits the way a co-located `ProjectionListener.handleSegmentCommitted` does (see its `records.length === 0` branch, which still advances to `event.segment`); this is a minor watermark-staleness difference between co-located and wire-fed consumption, not a correctness issue — the watermark still keys strictly off committed segment/event ids from the same node's own data, no non-owned data is ever attributed to the wrong node. With that correction, the rest of Decision 4 stands: `storageTask.listenEntry` already pipes the (conditional) broadcast live-tail to every attached entry node, so a KV-node process, connecting outward to entry FOX ports the same way `ndb.ts`'s `mkGate`/`mkSync` helpers already do for storage nodes, can subscribe to that same event on the sys realm — `ProjectionListener` already accepts a `SegmentCommittedSource` (currently `dbFactory`, an in-process `EventEmitter`); a wire-fed adapter implementing the same `on(SEGMENT_COMMITTED, handler)` surface is a drop-in swap, not a new contract. This is the central reason this proposal does not need to touch `hyper.h.ts`.

### 5. Node-level responsibility gate scoped to registration, not to every read
The `storage` pattern gate (`Requirement: Node-Level Storage Responsibility Gate` in the spec delta) applies to registering new projection/schema state (`KV_ADD`/`SCHEMA_ADD`) — the point where a human or `foxctl` operator picks *which* KV-node a projection's data should live on. It intentionally does not re-litigate the existing per-event `uriPattern` match `KvProjection.applyEvent` already performs on every commit; that stays exactly as-is. Two independent filters (node-level "am I even supposed to host anything for this realm/pattern" and projection-level "does this specific event match this specific registered projection") compose cleanly and keep each check's blast radius small.

**kv-node verification:** Confirmed against `lib/masterfree/admin_api.ts` — `KV_ADD` and `SCHEMA_ADD` are the only two handlers that create new registry/schema state (`StorageRegistry.register`/`SchemaRepository.register`); every other handler (`KV_LIST`, `KV_ACTIVATE`, `KV_RESET`, `SCHEMA_LIST`, `SCHEMA_DROP`, `SEGMENT_LIST`, `EVENT_SHARD_LIST`) only reads existing state or acts on an already-registered name, so gating just at `KV_ADD`/`SCHEMA_ADD` genuinely covers every state-creating path. One clarification worth making explicit: this gate applies only to the schema-backed projection registry (`StorageRegistry`/`KvProjection`, reached via `AdminEvent.KV_ADD`) — not to the separate, generic per-topic retained-value KV store (`SqliteKvFabric`/`kv_${realmName}` table in `lib/sqlite/sqlitekv.ts`) that every realm engine already maintains locally regardless of `dbNodes` topology. Both are called "KV" in this codebase but are unrelated data paths; only the former is in scope for `dbNodes` responsibility gating.

### 6. Duplicate `SEGMENT_COMMITTED` delivery is safe by construction, not something this proposal must dedup
A KV-node attaching to more than one entry node for availability (so it keeps receiving `SEGMENT_COMMITTED` if one entry goes down) will observe the same committed segment once per attached entry. This does not need new dedup logic: `KvProjection.applyEvent`'s writes are `INSERT OR REPLACE` upserts keyed by the schema's primary key, and `ProjectionListener.handleSegmentCommitted`'s `advancePosition` call is an unconditional, monotonically-non-decreasing `UPDATE current_position = ?` — reapplying the same committed segment a second time is a no-op in effect, just redundant work. Verified directly against the current `lib/sqlite/projection_listener.ts` implementation rather than assumed.

**kv-node correction:** Verified directly against `lib/sqlite/projection_listener.ts` and `lib/sqlite/sqlitekv.ts`, and the "safe by construction" framing needs a real caveat, not just confirmation. Two parts of the claim hold: `KvProjection.applyEvent`'s writes really are `INSERT OR REPLACE`/keyed `DELETE` (idempotent for re-processing one identical event), and `advancePosition` really is unconditional — it always issues the `UPDATE`, skipping only the trivial case where the incoming id equals the in-memory `currentPosition` it already holds. But `advancePosition` is **not** monotonic by construction: nothing in it compares the incoming `eventId` against the stored one before writing; it is monotonic only because, today, it is only ever called in strictly increasing order by a single ordered source. That distinction is exactly where the risk lives: re-delivery of the *same, already-fully-applied* segment (identical event set, identical values, from a second connection that saw the exact same commit) is genuinely a safe no-op, as claimed. But "attaching to more than one entry node for availability" describes *concurrent* consumption from two independent connections, and nothing guarantees those two connections stay relatively ordered with each other — e.g. connection A delivers segment S1 then S2 in order, while connection B (briefly slower, or reconnecting after a gap) redelivers S1 *after* the KV-node has already applied S2 from A. If S1 and S2 both touch the same projected key, `KvProjection.applyEvent` has no per-key event-id/version check before its upsert — it will blindly overwrite S2's newer payload with S1's older one, and the following `advancePosition(S1's eventId)` will regress `current_position` backward, contradicting the "monotonically-non-decreasing" characterization. This doesn't bite today only because a single co-located `ProjectionListener` has exactly one ordered source (`dbFactory`, an in-process `EventEmitter`); it is a real gap for the multi-entry-attachment scenario Decision 6 is explicitly about, not a nitpick.

**Recommendation:** until `kv-node`'s implementation change adds either (a) a per-key applied-event-id/version check before upsert, or (b) an explicit high-water-mark comparison in `advancePosition` (and in `handleSegmentCommitted`'s per-realm processing) that refuses to move a projection's position backward, redundant entry attachments should be consumed as **active/standby failover** — exactly one connection driving `handleSegmentCommitted` at a time, switching to a backup only once the primary is confirmed down — rather than concurrently. That preserves the single-ordered-stream assumption the existing idempotency argument actually depends on, without requiring any schema/code change in this proposal. Flagged as a follow-on for `kv-node`'s implementation change; see `tasks.md` 6.2 (added).

## Risks / Trade-offs

- **[Risk]** A misconfigured `dbNodes.storage` pattern (e.g. two nodes with deliberately disjoint patterns, one node down) could leave a realm+pattern combination with *zero* covering KV-node, silently dropping projection availability for it → **Mitigation**: `validateStorageForNode` catches malformed *syntax* at startup, but cross-node coverage-gap detection (no node covers X) is a cluster-wide check, not a single-node one — flagged in Open Questions below rather than solved here, since it does not change this proposal's spec surface. **kv-node correction:** the original mitigation text pointed at "`kv-node`'s `EVENT_SHARD_LIST`-style admin listing" as if a single KV-node's own listing could detect this; it can't — a KV-node has no visibility into realms/patterns it never sees, so it cannot self-report a gap in its own coverage by definition. Real coverage-gap detection needs to live outside any single node, in one (or both) of two places: (a) a **static, config-only check** over `dbNodes.storage` patterns alone (do the declared patterns' union cover `"*:#"`, or whatever the operator's completeness bar is?) — this needs no running node at all and could be a `Config`-side lint or a `foxctl doctor` command that just reads `config.json`; or (b) a **live cross-node reconciliation**, run by `foxctl`/an operator, comparing the new `KV_NODE_LIST` RPC (config truth — see Open Questions) against each reachable node's existing `KV_LIST`/`SCHEMA_LIST` output, to catch registrations that were valid when made but got orphaned by a later config change narrowing some node's patterns. Both are genuine follow-on work for `kv-node`/`foxctl`, not solved here — the correction is about *where* the check belongs, not whether it's needed.
- **[Risk]** Wildcard (`*:*`) realm coverage on a KV-node conflicts with the fact that nothing today broadcasts "a new realm was created" — so a KV-node with `*:*` cannot proactively register admin RPC surfaces for realms it hasn't yet observed a committed event or an explicit `KV_ADD`/`SCHEMA_ADD` call for → **Mitigation**: out of scope for this proposal by design (see Non-Goals); `kv-node`'s implementation change must resolve this before wiring `AdminApiServer` into a standalone KV-node process. Concretely deferred, not silently dropped — captured in Open Questions.
- **[Trade-off]** Reusing the broadcast `SEGMENT_COMMITTED` (rather than a per-KV-node-filtered topic, à la `KEEP_ADVANCE_HISTORY.<shardTag>`) means every attached KV-node receives every non-empty committed segment from every entry it's attached to, regardless of its own `storage` patterns, and filters client-side. This matches today's `ProjectionListener` behavior exactly (no regression) but does not reduce wire/CPU cost the way shard-topic routing did for `KEEP_ADVANCE_HISTORY`. Resolved by `event-history-node` (see Open Questions): broadcast + client-side filtering stays sufficient for now — revisit with per-*realm* topic routing (not per-pattern) if realm/KV-node counts grow enough to matter.

## Migration Plan

Purely additive: new `Config` methods, no changes to existing method signatures, no changes to the on-disk config schema (the `dbNodes` section is already checked in). Existing single-process (`OneDbRouter`) and current masterfree (`entry`/`sync`/`ndb`) deployments are unaffected — nothing calls the new accessors until a KV-node implementation change consumes them. No rollback concerns beyond reverting the `config.ts` addition and the two spec deltas.

## Open Questions

- **Resolved by `event-history-node`:** broadcast + client-side filtering is sufficient for now; do not add per-*pattern* (URI-level) topic routing to `SEGMENT_COMMITTED`, and hold off on per-*realm* routing too until it's actually load-bearing. Rationale:
  - **Why per-pattern routing is meaningfully harder to retrofit here than shard-topic routing was for `KEEP_ADVANCE_HISTORY`.** `KEEP_ADVANCE_HISTORY.<shardTag>` works because each `KEEP_ADVANCE_HISTORY` message is already exactly one event routed to exactly one numeric shard (a small, static, enumerable partition computed once by hashing at the entry node) — publishing it to `KEEP_ADVANCE_HISTORY.<shard>` instead of a bare topic is a one-line change in the publish call, no restructuring. `SEGMENT_COMMITTED` is shaped completely differently: one message is a *batch* (`CommittedSegmentEvent.events: CommittedSegmentRecord[]`) that can span multiple realms and multiple URIs accumulated over an entire advance window (see the `BODY_SEGMENT_COMMITTED` comment in `hyper.h.ts`: "may carry events from more than one realm"). A `<realm>:<key-pattern>` storage pattern is also not a small enumerable key the way a shard number is — it's an open-ended wildcard match requiring `topic_pattern.ts`'s `match()`, evaluated per-record, not per-message. Routing a batched, multi-realm, wildcard-matched message to a per-pattern topic would mean decomposing every commit into one publish per distinct matching pattern (or per record), which is a materially bigger structural change than picking one topic suffix per message — and it is exactly the kind of `EventStorageTask`/`commit_segment` restructuring this proposal's Non-Goals and Impact sections already decline to make.
  - **Per-realm routing (`SEGMENT_COMMITTED.<realm>`), by contrast, would be a cheap, direct mirror of the shard-topic precedent if it's ever needed** — `commit_segment`/`dbSaveSegment` already group buffered rows by realm internally (the same `realmEvents` grouping used for `updateSegmentResolved`/`insertSegmentOver`), so splitting the outgoing publish per realm is a small, local change confined to the `ADVANCE_SEGMENT_RESOLVED` handler in `storage.ts`, not a wire-format change (`BODY_SEGMENT_COMMITTED` stays the same shape, just narrower per publish). It would help a KV-node whose `storage` patterns name concrete, non-wildcard realms; it does *nothing* for a wildcard (`*`) realm pattern, which still needs every realm's traffic — and the only `dbNodes` example checked in today (`KV1`/`KV2`, both `"*:*"`) is exactly that case, read in Decision 3 as intentional full-replication for HA/read-scaling rather than partitioning. Because full replication is the one concrete deployment shape on record, per-realm routing would not currently reduce anyone's traffic.
  - **Scale reality check:** this cluster's plausible realm and KV-node counts are small (a handful of realms, a handful of KV-node replicas for HA) — nowhere near the volume where per-message topic fan-out cost dominates. Client-side filtering is also not new overhead: `ProjectionListener.handleSegmentCommitted`'s `uriPattern` check already runs per record today for the co-located case: a wire-fed KV-node reuses the identical filter, it just does so after a network hop instead of an in-process `EventEmitter` call.
  - **When to revisit:** if `dbNodes` deployments move away from full-replication `"*:*"` patterns toward genuine per-realm partitioning across many realms, or if realm/KV-node counts grow enough that broadcast volume becomes measurable, add `SEGMENT_COMMITTED.<realm>` topic routing (mirroring `Event.keepAdvanceHistoryTopic`) at that point — never per-pattern routing; pattern matching stays a client-side concern on top of the (possibly realm-scoped) broadcast, exactly as it is today.
- **Resolved (kv-node):** restrict wildcard (`*`) realm storage patterns to catch-up/read-scaling replicas, and require `foxctl`/admin tooling to target a specific KV-node by id (`getDbNodeById`) for the *first* `KV_ADD`/`SCHEMA_ADD` registration of a brand-new realm. Grounded in what exists today, not abstractly: `OneDbRouter`'s `router.createRealm(realmName)` (`lib/mono/onedbrouter.ts`) constructs a realm's `AdminApiServer` lazily, the moment *anything* touches that realm name in the same process — realm existence and admin-surface construction are literally the same act there, with no separate "announce" step, because `OneDbRouter` is also the client-facing router that first sees the realm name. A standalone KV-node has no equivalent signal: it never terminates client connections, and `ProjectionListener`'s own realm discovery (`forEachRealm` in `lib/sqlite/history.ts`, driven off `event_history_${realmName}` tables that already exist on disk) requires at least one committed event for that realm to already be persisted — exactly the chicken-and-egg the question describes for a realm nothing has been committed for yet. Adding a new "realm announced" broadcast would need some component (most plausibly an entry node, since it's the one that actually observes a new realm name first) to originate a new event type, which runs directly against this proposal's own Non-Goal of not touching `hyper.h.ts`/`EventStorageTask` and against Decision 4's "no new event type" position — so that candidate is rejected here, not left open. Given that, the other two candidates aren't actually exclusive — they compose: a wildcard `storage` pattern is a legitimate way to declare "replicate whatever realms exist," but it must never be the *only* node capable of accepting a first-time registration for a realm with no committed history yet, because nothing will ever prompt a wildcard-only node to try. `foxctl`/operators should address a specific node id for first-time `KV_ADD`/`SCHEMA_ADD` on a new realm — mirroring how `eventNodes`/shard placement is already an explicit, config-read operator decision rather than autodiscovered — and wildcard-pattern nodes then pick the realm up passively once real `SEGMENT_COMMITTED` traffic (or, for the explicitly-targeted node, the registration call itself) gives them something to react to.
  **Still genuinely open, left to `kv-node`'s implementation change:** even with an explicit target node id, that KV-node process still needs to construct a `BaseRealm`+`AdminApiServer` pair for a realm it has never seen before, triggered by the very first admin RPC for it rather than by a client pub/sub or RPC call reaching `createRealm` the way `OneDbRouter` triggers it today. The mechanism for that on-demand, admin-RPC-triggered realm bootstrap inside a standalone KV-node process still needs to be designed and built — this proposal doesn't attempt that, but the recommendation above narrows its scope to "bootstrap an explicitly-targeted realm on first admin call," not "materialize any realm out of nowhere for a wildcard listener."
- **Sketch (kv-node), not built in this pass:** a `KV_NODE_LIST` admin RPC, living in `lib/masterfree/admin_api.ts` next to `EVENT_SHARD_LIST` (same file, same `_register()` method, same pattern of reading straight from `getConfigInstance()` rather than any per-realm DB state), with request/response types added to `lib/masterfree/hyper.h.ts` beside `AdminEventShardEntry`/`AdminEventShardListResponse`:
  - `AdminEvent.KV_NODE_LIST = 'fox.admin.kvnode.list'` (naming mirrors `fox.admin.event.shard.list`).
  - Request: none (`Record<string, never>`), matching `EVENT_SHARD_LIST`'s no-argument, list-everything style — filtering by realm/pattern is left to the caller (`foxctl`), not the server, exactly as `EVENT_SHARD_LIST` returns every shard rather than accepting a query.
  - Response: `{ nodes: AdminDbNodeEntry[] }` where `AdminDbNodeEntry = { nodeId: string; host: string; port: string; pattern: string }` — one row per `(nodeId, storage pattern)` pair, flattened the same way `EVENT_SHARD_LIST` flattens to one row per `(nodeId, shardTag)` rather than nesting patterns under node. That lets `foxctl` run the same `parseStoragePattern`/`nodeOwnsRealmAndUri` matcher this proposal adds to `Config` (tasks 2.1/2.2) client-side over the returned rows, to answer "who covers realm R, pattern P" — and, per the Risk 1 correction above, to feed a coverage-gap check.
  - Implementation is trivially small: it's `config.getDbNodes()` flattened, exactly as `EVENT_SHARD_LIST` is `config.getEventNodes()` flattened. That's also why it doesn't need `kv-node`'s dedicated process to exist first — any process with the config loaded and `AdminApiServer` wired in (today, `OneDbRouter`; tomorrow, the KV-node) can serve it identically. Confirms this is a genuine "natural follow-on," not a placeholder for something harder.
