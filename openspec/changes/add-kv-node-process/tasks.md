## 3. RealmHistorySource seam and wire-sourced catch-up

- [x] 3.2 Extract today's local-db behavior (`History.getEventHistory` + `StorageRegistry.latestRealmEventId`-driven activation target) into a `LocalDbHistorySource` implementation; thread it through `ProjectionListener`'s constructor as the default so `OneDbRouter`/`ndb.ts` callers are unaffected. Verify existing `ProjectionListener`/activation tests (e.g. those exercising `test/` cases for `kv-storage-registry`) still pass unchanged. — Done: `LocalDbHistorySource` is the default; `StorageRegistry.startActivation` gained an optional target resolver and `latestRealmEventId` is now exported. All pre-existing tests pass unchanged.
- [x] 3.3 Implement `WireHistoryFetchSource`, pulling per-shard history via `client.callrpc(Event.historyFetchTopic(shardTag), {realm, afterEventId}, {progress})` against the KV-node's active entry connection for every shard, merging results into ascending `eventId` order (reusing or mirroring `SharedSegmentBuffer`'s merge logic from `lib/masterfree/net_sub.ts`), and treating `ERROR_NO_SUCH_PROCEDURE` per shard as "nothing to fetch," matching `SharedSegmentBuffer.ensureLoading`'s existing handling. Verify with a unit test against fake per-shard RPC responses, including an out-of-order-arrival and a no-such-procedure case. — Done in `lib/masterfree/wire_history_source.ts`. Deviation from `SharedSegmentBuffer`: a shard failing with anything other than `ERROR_NO_SUCH_PROCEDURE` fails the fetch rather than being logged and skipped, so a projection cannot go online with silently missing history. `latestEventId` fetches the snapshot once and `fetchSince` replays it.
- [x] 3.4 Wire `_runActivation` (or its KV-node-specific equivalent) to use the injected `RealmHistorySource` instead of calling `History.getEventHistory`/`latestRealmEventId` directly; verify a KV-node-configured `ProjectionListener` instance backfills correctly against a fake `WireHistoryFetchSource` in a unit test, including the "first activation of a realm with pre-existing history" scenario from the spec. — Done, including first activation of a realm with pre-existing remote history (`test/76.realm_history_source.ts`).
- [x] 3.5 Verify catch-up and live-tail delivery do not race: a projection stays `refreshing` (excluded from `handleSegmentCommitted`'s `status === Online` filter) for the full duration of catch-up, and only transitions to `online` after catch-up's per-shard fetches all resolve.
