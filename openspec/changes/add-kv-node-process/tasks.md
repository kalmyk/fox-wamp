## 2. WireSegmentCommittedSource adapter

- [ ] 2.1 Create `lib/masterfree/wire_segment_source.ts` exporting a class implementing `SegmentCommittedSource` (`on(SEGMENT_COMMITTED, handler)`) that wraps one or more `HyperNetClient` connections; verify it satisfies the `SegmentCommittedSource` interface at compile time (drop-in as `ProjectionListener`'s constructor argument).
- [ ] 2.2 Implement active/standby connection tracking per design.md Decision 3: exactly one connection is "active" at a time; only its `Event.SEGMENT_COMMITTED` deliveries are forwarded to registered handlers; standby deliveries are discarded, not queued. Verify with a unit test using two fake/mock `HyperNetClient`-like sources: only active-source events reach the handler.
- [ ] 2.3 Implement failover: on the active connection's disconnect, promote the first still-connected standby to active. Verify with a unit test simulating an active-source disconnect and asserting the previously-standby source's subsequent events now reach the handler.
- [ ] 2.4 Verify no ordering assumption is violated by re-reading `add-kv-node-topology/design.md` Decision 6 and confirming the discard-not-queue rule (2.2) directly prevents the regression scenario it describes — add a regression test reproducing that scenario (standby redelivers an older segment after the active source delivered a newer one) and asserting the standby delivery is dropped.
- [ ] 2.5 Implement the bounded per-realm high-water-mark ordering guard from design.md Decision 7: track the highest applied `eventId` per realm (a plain `Map<string, string>`, bounded by realm count) and drop (with a warning log) any incoming record whose `eventId` does not exceed the tracked value for its realm, applying the check per-record before grouping into the batch handed to `ProjectionListener`. Verify with a unit test delivering an out-of-order cross-realm/cross-shard batch on a single connection (no failover involved) and asserting the earlier-`eventId` record is dropped while later ones are applied; also verify guard state stays a fixed number of entries (one per realm) regardless of event volume in a longer-running test.
- [ ] 2.6 Re-check this guard against `openspec/changes/live-dispatch-eventid-ordering/` once that change is implemented — task tracked there, not here (no code task in this change beyond the interim guard itself); add a code comment pointing at that change so the guard's removal isn't missed.

- [ ] 3.1 Define a `RealmHistorySource` interface (e.g. in `lib/sqlite/projection_listener.ts` or a new small module) with a method to fetch a realm's committed events since a given `eventId`, per design.md Decision 6.
- [ ] 3.2 Extract today's local-db behavior (`History.getEventHistory` + `StorageRegistry.latestRealmEventId`-driven activation target) into a `LocalDbHistorySource` implementation; thread it through `ProjectionListener`'s constructor as the default so `OneDbRouter`/`ndb.ts` callers are unaffected. Verify existing `ProjectionListener`/activation tests (e.g. those exercising `test/` cases for `kv-storage-registry`) still pass unchanged.
- [ ] 3.3 Implement `WireHistoryFetchSource`, pulling per-shard history via `client.callrpc(Event.historyFetchTopic(shardTag), {realm, afterEventId}, {progress})` against the KV-node's active entry connection for every shard, merging results into ascending `eventId` order (reusing or mirroring `SharedSegmentBuffer`'s merge logic from `lib/masterfree/net_sub.ts`), and treating `ERROR_NO_SUCH_PROCEDURE` per shard as "nothing to fetch," matching `SharedSegmentBuffer.ensureLoading`'s existing handling. Verify with a unit test against fake per-shard RPC responses, including an out-of-order-arrival and a no-such-procedure case.
- [ ] 3.4 Wire `_runActivation` (or its KV-node-specific equivalent) to use the injected `RealmHistorySource` instead of calling `History.getEventHistory`/`latestRealmEventId` directly; verify a KV-node-configured `ProjectionListener` instance backfills correctly against a fake `WireHistoryFetchSource` in a unit test, including the "first activation of a realm with pre-existing history" scenario from the spec.
- [ ] 3.5 Verify catch-up and live-tail delivery do not race: a projection stays `refreshing` (excluded from `handleSegmentCommitted`'s `status === Online` filter) for the full duration of catch-up, and only transitions to `online` after catch-up's per-shard fetches all resolve. Add a test asserting a `SEGMENT_COMMITTED` delivered mid-catch-up is not applied until catch-up completes.
