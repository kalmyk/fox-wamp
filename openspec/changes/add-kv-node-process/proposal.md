## Why

`add-kv-node-topology` (implemented, not yet archived) gave `Config` a `dbNodes` accessor surface (`getDbNodes()`, `getDbNodeById()`, `findStoragePatternsForNode()`, `parseStoragePattern()`, `nodeOwnsRealmAndUri()`, `validateStorageForNode()`) but deliberately stopped short of building the KV-node process itself — it left `bin/masterfree/kvnode.ts`, the wire-fed committed-segment adapter, `AdminApiServer`/`StorageRegistry`/`SchemaRepository` wiring outside `OneDbRouter`, wildcard-realm bootstrap, multi-entry failover safety, and `KV_NODE_LIST` placement as open follow-on work. Today, in masterfree deployments, the persistent KV/admin surface is not reachable at all — `bin/masterfree/entry.ts` never wires `AdminApiServer` onto its realms, and `bin/masterfree/ndb.ts`'s co-located `ProjectionListener` is fed only by that one storage node's own local `dbFactory` emitter, which is silently incomplete for any realm whose traffic spans shards owned by other storage nodes. A real, standalone KV-node process is needed to make persistent KV projections and their admin API work correctly in masterfree mode at all.

## What Changes

- Add a new masterfree process entrypoint `bin/masterfree/kvnode.ts` that reads `NODE_ID`/`CONFIG` (and its own `DB_FILE`) env vars, validates itself against `dbNodes` config at startup (`config.getDbNodeById`, `config.validateStorageForNode`), and runs two independent roles concurrently:
  - **Inbound admin gate**: listens on its own configured `dbNodes.<id>.host/port` via `listenHyperNetServer`/`FoxGate`, exactly mirroring `bin/masterfree/sync.ts`'s listen pattern — this is the only way `AdminApiServer`'s RPC-style (`register()`) admin methods can ever be reached by a client, since `EventStorageTask.listenEntry`'s `pipe()` mechanism forwards pub/sub only, never RPC registrations.
  - **Outbound committed-segment subscriber**: connects outward to every configured entry node (reusing `ndb.ts`'s `mkGate`/`HyperNetClient` pattern), logs into the `sys` realm, and subscribes to the wire `Event.SEGMENT_COMMITTED` broadcast that `EventStorageTask.listenEntry` already pipes to every attached entry — **not** the in-process `dbFactory` `EventEmitter` `bin/masterfree/ndb.ts` uses today, which only reflects that one storage node's own shard range.
- Add a `WireSegmentCommittedSource` adapter (new, small module) implementing the existing `SegmentCommittedSource` interface (`lib/masterfree/segment_types.ts`) over one-or-more `HyperNetClient` wire subscriptions, so `ProjectionListener`'s constructor takes it as a drop-in replacement for `dbFactory` — no change to `ProjectionListener` itself.
- Define **active/standby failover** semantics for multi-entry attachment: exactly one entry connection drives `ProjectionListener.handleSegmentCommitted` at a time; a standby connection's deliveries are buffered/discarded until promoted. This closes the **multi-connection redelivery** variant of the gap `add-kv-node-topology/design.md` Decision 6 flagged (`advancePosition`/`KvProjection.applyEvent` have no per-key high-water-mark guard, so concurrent multi-source delivery can regress a projection) — it does **not** close a related cross-shard `eventId`-ordering variant of the same gap, which exists even with a single active connection and is tracked separately in `openspec/changes/live-dispatch-eventid-ordering/`; see `design.md` Decision 3's kv-node correction.
- Define a **realm-bootstrap path** for the KV-node process: a `KvNodeRouter` (mirroring `OneDbRouter`'s `createRealm`/`initRealm` override pattern) that lazily constructs `BaseRealm`+`DbEngine`+`AdminApiServer` the first time any client logs into a realm on the KV-node's own admin gate — reusing `Router.getRealm()`'s existing lazy-creation hook rather than inventing a new "realm announced" event.
- Define the **node-level registration gate enforcement point**: `KV_ADD`/`SCHEMA_ADD` handlers reject a registration whose realm+`urlPattern` isn't covered by `config.nodeOwnsRealmAndUri(myNodeId, realm, uriParts)`, and additionally reject a realm's **first-ever** registration on a node that only covers it via a wildcard (`*`) realm pattern when the same `dbNodes` config declares another node with an exact-realm pattern for that realm — a fully local check (every node already loads the whole `dbNodes` config), no cluster RPC required.
- Decide and implement the placement of `AdminEvent.KV_NODE_LIST`: registered on every KV-node's own admin gate (next to `KV_LIST`/`SCHEMA_LIST`), trivially `config.getDbNodes()` flattened — not a cluster-wide coordinator RPC, and not computed client-side by `foxctl` alone (a config file isn't always available to an operator's client machine, and returning it from a live node confirms the node is actually up and using that config).
- Give `ProjectionListener`'s activation path a pluggable `RealmHistorySource` seam (a new, small interface) so a KV-node's projections can catch up — both on first activation and after a connection outage — by pulling history over the existing per-shard `Event.historyFetchTopic` RPC, instead of the local `event_history_${realmName}` table scan `_runActivation` uses today, which a standalone KV-node never has populated (finding from `event-history-node`'s review; see `design.md` Decision 6). `OneDbRouter`/`ndb.ts`-colocated `ProjectionListener` instances keep today's local-db behavior unchanged via the existing-behavior implementation of that same seam.
- Give `WireSegmentCommittedSource` a small, per-realm, heap-bounded high-water-mark guard against cross-shard `eventId` regression at the `SEGMENT_COMMITTED` fan-in point — an interim safeguard for a pre-existing gap (not introduced by this change) that `openspec/changes/live-dispatch-eventid-ordering/` is separately chartered to fix properly with a k-way merge (finding from `kv-node`'s review; see `design.md` Decision 7).
- Document the KV-node's concrete process shape (listen + outbound-subscribe duality, failover, bootstrap, registration gating) in `distributed-mode.md`, additive to (not duplicating) the KV-node-as-fourth-node-type framing already pending from `add-kv-node-topology`.
- Out of scope: implementing any of the above in code (this is a planning/design pass only, mirroring how `add-kv-node-topology` was scoped then separately implemented); changing `KvProjection.applyEvent`/`advancePosition` to add a per-key version guard (the active/standby failover design avoids needing one for now); per-realm or per-pattern `SEGMENT_COMMITTED` topic routing (already resolved against, in the prior change, as unneeded at current scale).

## Capabilities

### New Capabilities
- `kvnode-process`: The `bin/masterfree/kvnode.ts` entrypoint, its dual listen/subscribe role, the `WireSegmentCommittedSource` adapter contract, active/standby multi-entry failover, the `KvNodeRouter` realm-bootstrap path, registration-time node/wildcard gating, and `KV_NODE_LIST` placement.

### Modified Capabilities
- `distributed-mode`: Adds concrete KV-node process-level detail (dual listen/subscribe roles, failover, bootstrap trigger) on top of the KV-node's architectural position already pending from `add-kv-node-topology`'s still-unarchived delta.

## Impact

- New files: `bin/masterfree/kvnode.ts`, a new small adapter module (e.g. `lib/masterfree/wire_segment_source.ts`), a new `KvNodeRouter` (e.g. `lib/mono/kvnoderouter.ts` or `lib/masterfree/kvnoderouter.ts` — implementation change to decide final path), a new `WireHistoryFetchSource` implementing the new `RealmHistorySource` seam.
- `lib/masterfree/admin_api.ts`: `KV_ADD`/`SCHEMA_ADD` handlers gain the node-ownership/wildcard-precedence gate (currently ungated — any registration succeeds regardless of `dbNodes` config); `KV_NODE_LIST` handler added alongside `EVENT_SHARD_LIST`.
- `lib/masterfree/hyper.h.ts`: adds `AdminEvent.KV_NODE_LIST` and `AdminDbNodeEntry`/`AdminKvNodeListResponse` types, mirroring `AdminEventShardEntry`/`AdminEventShardListResponse` — no changes to any StageOne/StageTwo/`BODY_*` election types.
- `lib/sqlite/projection_listener.ts`/`lib/sqlite/storage_registry.ts`: gain the additive `RealmHistorySource` seam described above (new constructor parameter, existing `LocalDbHistorySource` behavior preserved as the default for current callers) — `KvProjection`'s write semantics and `handleSegmentCommitted`'s live-tail logic are unchanged.
- `supervisor/config.json`: no schema change (the `dbNodes` section with `host`/`port`/`storage` already exists and already carries what the listen role needs).
- `openspec/specs/distributed-mode.md`: gains KV-node process-shape detail once this change and `add-kv-node-topology` are both archived (this proposal assumes `add-kv-node-topology` archives first or concurrently; see design.md for delta sequencing).
- Testing (for the follow-on implementation change): unit tests for `WireSegmentCommittedSource` failover switching and its high-water-mark ordering guard, `WireHistoryFetchSource`'s per-shard merge, `admin_api.ts`'s new registration gate (covered/not-covered/wildcard-precedence cases), and an integration-style test standing up a `kvnode.ts`-equivalent process against a fake entry connection covering both first-activation backfill and live-tail delivery.
