## Context

`add-kv-node-topology` (implemented, tested in `test/67.dbnodes.ts`, not yet archived — `openspec/specs/distributed-mode.md` still lists only three architecture components) gave `Config` a full `dbNodes` accessor/matching surface but explicitly stopped short of building the process. Directly re-verified in this session:

- `bin/masterfree/ndb.ts` feeds its co-located `ProjectionListener` from `dbFactory`'s local `EventEmitter` — which only fires for segments *that node's own* `EventStorageTask.commit_segment` resolves, i.e. only the shards `config.findShardsForNode(conf_node_id)` returns. Since `supervisor/config.json`'s `eventNodes` shards overlap-but-differ across DB1–DB4 and realm traffic is round-robined across shards, a `ProjectionListener` fed this way sees an incomplete view of any realm whose traffic spans shards it doesn't own — silently, no error. **This proposal builds around that constraint rather than relitigating it**, per `add-kv-node-topology/design.md` Decision 4: a real KV-node must subscribe to the wire `Event.SEGMENT_COMMITTED` broadcast.
- `EventStorageTask.listenEntry` (`lib/masterfree/storage.ts`) already does `await this.api.pipe(client, Event.SEGMENT_COMMITTED, {exclude_me: false})` — piping the (conditional-on-non-empty) broadcast to every attached entry node. On the entry side, a plain `HyperNetClient.subscribe(Event.SEGMENT_COMMITTED, handler)` after `login({realm: INTRA_REALM_NAME})` receives it — no new event or topic needed.
- `ProjectionListener`'s constructor (`lib/sqlite/projection_listener.ts`) already accepts anything satisfying `SegmentCommittedSource` (`on(SEGMENT_COMMITTED, handler)`, `lib/masterfree/segment_types.ts`) — today always `dbFactory`. A wire-fed adapter is a drop-in swap.
- **New finding this session, load-bearing for this design**: `pipe()` forwards pub/sub only, never RPC registrations (explicit comment in `storage.ts` above `listenEntry`'s manual `client.register(...)` for `historyFetchTopic`). `AdminApiServer` (`lib/masterfree/admin_api.ts`) exposes its entire surface via `api.register(...)` — RPC, not pub/sub. Therefore **no pipe-based relay through an entry node can ever expose a KV-node's admin RPCs to a client** — a KV-node's admin surface must be reached by a *direct* connection to the KV-node itself. This is exactly why `dbNodes.<id>` entries in `supervisor/config.json` already carry their own `host`/`port` (`KV1: 127.0.0.1:1765`, `KV2: 127.0.0.1:1766`) — those fields are for a KV-node's own inbound listener, the same way `syncNodes.<id>.host/port` is both what `bin/masterfree/sync.ts` listens on (`listenHyperNetServer(new FoxGate(router), {port: nodeConf.port})`) *and* what peers dial. `bin/masterfree/ndb.ts` is the odd one out — it never calls `listenHyperNetServer` at all, so `eventNodes.<id>.host/port` is presently unused for inbound listening; the KV-node should follow `sync.ts`'s pattern, not `ndb.ts`'s.
- `foxctl` (`bin/foxctl.ts`) already connects directly via `HyperNetClient({host, port})` and `client.login({realm})` before calling `AdminEvent.*` RPCs — it dials whatever `--host`/`--port` the operator gives it. Pointing it at a KV-node's own address, instead of an entry node, requires no `foxctl` change at all.
- `Router.getRealm(realmName)` (`lib/router.ts`) already lazily calls `createRealm()` + `initRealm()` the first time any session logs into a realm name not yet in `this._realms`, and emits `REALM_CREATED`. `OneDbRouter` (`lib/mono/onedbrouter.ts`) overrides both hooks to build `BaseRealm`+`DbEngine` and then `AdminApiServer`. This is the exact mechanism `add-kv-node-topology/design.md`'s Open Question asked for ("a mechanism for on-demand, admin-RPC-triggered realm bootstrap") — it already exists and needs no new event; a KV-node just needs its own `Router` subclass applying the same override pattern.
- Every process loads the *entire* `supervisor/config.json`, including the full `dbNodes` map — `Config.getDbNodes()` returns all entries, not just the calling node's own. This means a KV-node can answer questions about *other* KV-nodes' configured patterns purely locally, with no cluster RPC, which matters for the wildcard first-registration check below.

**event-history-node verification:** Re-traced against the current `lib/masterfree/storage.ts`, `bin/masterfree/ndb.ts`, and `bin/masterfree/sync.ts` — both bullets above still hold exactly, line numbers aside. `EventStorageTask.listenEntry` (`storage.ts`, now lines 130-158) still does `await this.api.pipe(client, Event.SEGMENT_COMMITTED, {exclude_me: false})` (line 152), and it is still gated by the `ADVANCE_SEGMENT_RESOLVED` handler's `if (result.events.length > 0)` check (lines 108-123), matching the "conditional-on-non-empty" description exactly. `bin/masterfree/ndb.ts` has no import of, and no call to, `listenHyperNetServer` anywhere in the file — grepping `listenHyperNetServer` across `bin/masterfree/*.ts` finds it only in `sync.ts` (line 51, `listenHyperNetServer(new FoxGate(router), { port: nodeConf.port })`) and `entry.ts` (line 34, listening on its own `FOX_PORT` env var, not on any `config`-sourced host/port). One nuance worth adding: `eventNodes.<id>.host`/`.port` isn't *purely* vestigial config today — `lib/masterfree/admin_api.ts`'s `AdminEvent.EVENT_SHARD_LIST` handler already reads `config.getEventNodes()` and echoes each node's `host`/`port` straight into its response rows (`AdminEventShardEntry`), for `foxctl`/operator tooling to know where a shard's owning storage node is *expected* to run. That is a real, live, non-listening consumer of those fields. The design's phrasing ("presently unused for inbound listening") is accurate as literally stated and needs no change — just don't read it as "unused, full stop": `ndb.ts` reads its own `NODE_ID`'s shards via `config.findShardsForNode`, never its own `host`/`port`, and nothing dials a storage node's `eventNodes` address to connect to it (storage nodes only ever dial *out* to entry/sync nodes) — so the asymmetry the design flags is real, current, and has no lifecycle dependency on the port being unlistened.

See `openspec/changes/add-kv-node-topology/design.md` for the full grounding on the `dbNodes` grammar, overlap semantics, and the Decision 6 correction on `advancePosition`'s lack of a monotonic guard — not re-litigated here.

## Goals / Non-Goals

**Goals:**
- Give `bin/masterfree/kvnode.ts` a concrete, buildable shape: what it listens on, what it connects to, and in what order at startup.
- Make the admin surface (`AdminApiServer`) actually reachable in masterfree deployments, which today it is not.
- Close the multi-entry-attachment safety gap identified (not solved) by `add-kv-node-topology` with a concrete failover design, not a per-key version-check redesign of `KvProjection`.
- Give the wildcard-realm bootstrap question a concrete, local, no-new-RPC mechanism.
- Decide `KV_NODE_LIST`'s home with justification, not just sketch it.
- Give a standalone KV-node a working catch-up path for realm history it never saw live — both first-ever activation and closing a gap left by a connection outage — since it has no local `event_history_<realm>` table to fall back on (finding from `event-history-node`'s review; see Decision 6).
- Give a concrete, scoped stance on cross-shard `eventId` ordering at the `SEGMENT_COMMITTED` fan-in point a KV-node consumes from, rather than silently inheriting a known, separately-tracked gap (finding from `kv-node`'s review; see Decision 7).

**Non-Goals:**
- Writing the implementation (`kvnode.ts`, the adapter, `admin_api.ts` gate logic) — that is the follow-on `kv-node`/`event-history-node` implementation change, per `tasks.md`.
- Adding a per-key applied-event-id/version guard to `KvProjection.applyEvent`/`advancePosition`. The active/standby failover design in Decision 3 makes this unnecessary for now; it remains a valid alternative future hardening step, not required by this design.
- Changing `EventStorageTask`, `hyper.h.ts`'s election `BODY_*` types, or StageOne/StageTwo protocol in any way.
- Solving cross-node coverage-gap detection (flagged as a `foxctl`/operator-tooling follow-on in `add-kv-node-topology/design.md`'s Risks) — this design's wildcard first-registration check is narrower and purely local; it does not attempt full coverage auditing.
- Fixing cross-shard `eventId` ordering at the live-dispatch fan-in point itself — that is `live-dispatch-eventid-ordering`'s scope (a k-way merge across per-shard sorted streams in `NetEngineMill`). This design only decides how a KV-node behaves until that fix lands (Decision 7).
- **Revised, no longer a Non-Goal as originally stated**: this design does end up touching `lib/sqlite/projection_listener.ts`/`lib/sqlite/storage_registry.ts` (a pluggable history-source seam, Decision 6) — narrower than "untouched" as first written. `KvProjection`'s write semantics and `handleSegmentCommitted`'s live-tail logic remain unchanged.

## Decisions

### 1. KV-node runs two independent roles: an inbound `FoxGate` admin listener, and outbound `HyperNetClient` committed-segment subscriptions

Rationale is entirely in the Context section's `pipe()`-forwards-pub/sub-only finding: there is no way to reach `AdminApiServer`'s RPCs through an entry node's pipe relay, so a KV-node must listen for direct connections on its own `dbNodes.<id>.host/port`, mirroring `sync.ts`:

```
listenHyperNetServer(new FoxGate(kvNodeRouter), { port: Number(myDbNodeConf.port) })
```

Separately and concurrently, it dials every configured entry node the way `ndb.ts`'s `mkGate` does, but registers only a subscriber, not `storageTask.listenEntry`:

```
const client = new HyperNetClient({host, port})
client.onopen(async () => {
  await client.login({realm: INTRA_REALM_NAME})
  client.subscribe(Event.SEGMENT_COMMITTED, wireSource.dispatch)
})
client.connect()
```

**Alternative considered:** route admin RPCs through the entry node's own FOX gate by having the KV-node register its admin methods on a connection *into* the entry (the reverse direction of `pipe`). Rejected — `HyperClient.register()` registers on the realm the registering session is logged into; registering from a KV-node's outbound connection to an entry would put the RPC methods on the *entry's* realm object, invisible to anything not also connected to that same entry, and would make the entry a required hop for all KV admin traffic, contradicting the "no coordination between components beyond what's necessary" spirit of the existing design. A direct address is simpler, already provisioned in config, and matches `sync.ts`'s precedent exactly.

**kv-node verification:** Traced `lib/hyper/client.ts` directly to confirm both halves of this reasoning rather than take them on faith. `HyperClient.pipe(writeToClient, topic, pipeOpt)` is exactly `this.subscribe(topic, (body, opt) => writeToClient.publish(opt.topic, body, newOpt))` — a subscribe-then-republish pair; there is no `register`/`cmdRegRpc` analogue anywhere in the pipe path, and no other method on `HyperClient` (`callrpc`, `subscribe`, `publish`, `echo`, `unregister`, `unsubscribe`) forwards a registration either. Separately, `register(uri, cb)` calls `this.realm.cmdRegRpc(this.ctx, {...})`; for a `RemoteHyperClient`/`HyperNetClient` the constructor does `super(formatter, formatter)`, so `this.realm` *is* the `HyperSocketFormatter` — calling `register()` on an outbound connection sends a wire `REG` command asking the process on the *other end* of the socket to register the RPC against whatever realm that socket's own server-side session is logged into. For a KV-node's outbound connection into an entry, that is the entry's own realm object — exactly confirming the Alternative-considered analysis (the RPC would land on the entry, reachable only by sessions on that same entry, not on the KV-node itself). `pipe()` is the only forwarding primitive that exists in this file, and it is pub/sub-shaped end to end. Decision 1's conclusion holds as stated; no correction needed.

### 2. Realm bootstrap: a `KvNodeRouter extends Router`, not a new event

Mirrors `OneDbRouter` exactly:

```ts
class KvNodeRouter extends Router {
  createRealm(realmName: string): BaseRealm {
    return new BaseRealm(this, new DbEngine(makeId, modKv))
  }
  async initRealm(realmName: string, realm: BaseRealm): Promise<void> {
    await super.initRealm(realmName, realm)
    if (realmName !== INTRA_REALM_NAME) {
      new AdminApiServer(realm, realmName, db, projectionListenerFor(realmName), makeId)
    }
  }
}
```

The KV-node's `FoxGate` login handler calls `router.getRealm(realmName)` the same way every other gate does; the first login for a never-seen realm name triggers `createRealm`/`initRealm` lazily, exactly as `OneDbRouter` already does for its own client-facing realms today. No new "realm announced" event, no change to `hyper.h.ts` for this purpose — confirming the prior proposal's rejection of that candidate.

One structural difference from `OneDbRouter`: a KV-node's `ProjectionListener`/`WireSegmentCommittedSource` pairing is cluster-wide (one wire subscription feeds potentially many realms' projections, since `SEGMENT_COMMITTED` batches can span realms), while `AdminApiServer` instances are per-realm. This design keeps a single `ProjectionListener` instance for the whole KV-node process (constructed once at startup against the `WireSegmentCommittedSource`, exactly as `ndb.ts`/`OneDbRouter` each construct exactly one `ProjectionListener` today) and has `KvNodeRouter.initRealm` pass that same shared instance into each realm's new `AdminApiServer` — not one `ProjectionListener` per realm. This matches `ProjectionListener.handleSegmentCommitted`'s existing internal per-realm grouping (`forEachRealm`), which already assumes exactly this shape.

**Alternative considered:** require an explicit `KV_BOOTSTRAP_REALM` admin call before any other admin RPC is accepted for a new realm. Rejected — adds an operator step with no behavioral benefit over letting `login` itself trigger bootstrap, and diverges from the `OneDbRouter` precedent for no reason.

**kv-node verification:** `lib/mono/onedbrouter.ts` is not just an analogous precedent, it already *is* a live instance of exactly this shape, not a hypothetical: `OneDbRouter`'s constructor builds one `ProjectionListener` (`this.projectionListener = new ProjectionListener(dbFactory, dbFactory.getMainDb(), this.makeId)`), and `initRealm` passes that same field into a fresh `AdminApiServer` for every realm it lazily creates (`new AdminApiServer(realm, realmName, this.modKv.getDbFactory().getMainDb(), this.projectionListener, this.makeId)`) — one instance, every realm, already running today. And `ProjectionListener.handleSegmentCommitted` internally calls `forEachRealm(this.db, async (realmName) => {...})`, using its own per-realm `registries`/`schemas` `Map`s (keyed by `realmName`, lazily populated via `getRegistry`/`getSchemaRepo`) to fan one incoming `CommittedSegmentEvent` out across every realm that has history tables — it was already written to serve multiple realms from a single instance, independent of how many `AdminApiServer`s happen to reference it. `KvNodeRouter` sharing one `ProjectionListener` across realms is reusing a shape the codebase already depends on, not introducing a new assumption; no correction needed.

### 3. Multi-entry attachment: active/standby failover, chosen over a version-guard redesign

Per `add-kv-node-topology/design.md` Decision 6's correction: `KvProjection.applyEvent`'s upserts are idempotent for *identical* redelivery, but `advancePosition` has no check against the incoming `eventId` before writing — concurrent delivery from two independently-ordered connections (e.g. a briefly-lagging standby redelivering an older segment after a newer one was already applied from the primary) can regress `current_position` and clobber a projection with stale data.

**Decision:** the `WireSegmentCommittedSource` adapter owns exactly one **active** connection at a time out of however many entry nodes it's attached to; only the active connection's `SEGMENT_COMMITTED` deliveries are forwarded into `ProjectionListener.handleSegmentCommitted`. Standby connections stay logged in (so failover has no re-login latency) but their deliveries are discarded, not queued — queuing would reintroduce exactly the out-of-order redelivery risk this exists to prevent, once the queue is later drained after a promotion. Concretely:

- Liveness of the active connection is the underlying `HyperNetClient`'s own connection state (already reconnect-aware — `net_transport.ts` has `maxReconnectAttempts`/auto-reconnect). The adapter listens for the active client's disconnect and, on disconnect, promotes the first still-connected standby to active.
- Promotion does not attempt to reconcile "what did I miss between disconnect and promotion" — the newly active connection resumes live-tail delivery from whatever it receives next. A gap during failover is a liveness/availability concern (a brief pause in projection freshness), not a correctness one, because `ProjectionListener`'s activation/catch-up path (`activateProjection`/`_runActivation`, driven by `current_position`) already exists to backfill from stored history for exactly this kind of gap — reusing it here rather than building a second catch-up mechanism.
- There is exactly one `ProjectionListener.handleSegmentCommitted` in flight at a time by construction (JS single-threaded event loop, and the standby-discard rule above), so no additional locking is needed beyond what `withWriteLock` already provides inside `KvProjection`.

**event-history-node correction:** The claim two bullets up — that "`ProjectionListener`'s activation/catch-up path (`activateProjection`/`_runActivation`, driven by `current_position`) already exists to backfill from stored history for exactly this kind of gap" — does not hold for a standalone KV-node process as scoped by this design, and the resulting gap is bigger than "a brief pause in projection freshness." Traced end to end:
  - `_runActivation` (`lib/sqlite/projection_listener.ts`) only backfills `if (activationTarget)`. `activationTarget` comes from `StorageRegistry.startActivation` → `latestRealmEventId(this.db, realmName)` (`lib/sqlite/storage_registry.ts`), which runs `SELECT MAX(msg_id) FROM event_history_${realmName}` — but only after first checking `sqlite_master` for that table's existence, returning `null` (not throwing) when it's absent.
  - `event_history_${realmName}` is created and populated *only* by `EventStorageTask`/`DbEngine` (`History.createHistoryTables`/`History.saveEventHistory`, called from `storage.ts`'s `ensureRealm`/`dbSaveSegment` on a storage node, or from `lib/mono/dbengine.ts` in single-process/`OneDbRouter` mode) — never by anything this design proposes for `kvnode.ts`/`WireSegmentCommittedSource`/`KvNodeRouter`. A standalone KV-node's own local db, as scoped here, never gets an `event_history_<realm>` table at all.
  - Consequence: on a KV-node, `latestRealmEventId` returns `null` for every realm, so `_runActivation`'s backfill block never runs — not only during a failover gap, but on a projection's very first `KV_ACTIVATE` too. This is not a liveness blip bounded by existing catch-up machinery; it is a standing behavioral difference from `OneDbRouter` (where `DbEngine` and `ProjectionListener` already share one db, so backfill genuinely works there today). A KV-node-hosted projection only ever sees events published *after* its `WireSegmentCommittedSource` subscription was live — zero backfill of realm history predating registration/activation, and zero recovery of any gap incurred while every outbound entry connection was briefly down (this Decision's own Risk bullet above), or while just *one* entry connection the KV-node happens to be using was down on the *storage-node* side of that link: `HyperNetClient`'s auto-reconnect (`lib/hyper/net_transport.ts`) re-runs `onopen` (so `storageTask.listenEntry` re-pipes) on reconnect, but replays nothing published during the outage — `pipe()` (`lib/hyper/client.ts`) is a plain live `subscribe()`-and-republish with no queue or persistence, so a storage node's own brief reconnect to an entry can silently and permanently drop `SEGMENT_COMMITTED` events for every consumer attached through that entry, KV-node included, independent of the KV-node's own active/standby logic above.
  - A working fix already exists in the codebase and should be reused rather than invented: every storage node already registers a per-shard `Event.historyFetchTopic(shard)` RPC directly on each entry it's attached to (`EventStorageTask.announceToEntry`, `storage.ts`), and `lib/masterfree/net_sub.ts`'s `SharedSegmentBuffer`/`SeenEventWindow` already implement exactly this kind of pull-based, de-duplicated, per-shard catch-up for an entry node's own live-tail subscribers. `WireSegmentCommittedSource`'s activation path (and its failover-promotion path) should call `Event.historyFetchTopic(shard)` against a connected entry the same way, rather than relying on `ProjectionListener`'s local-db backfill, which is a no-op for this node type. This most likely means the KV-node's activation/failover flow needs to drive its own pull-based catch-up around `activateProjection`/promotion, not that `ProjectionListener` itself needs to change (consistent with this design's Non-Goal of leaving `ProjectionListener` untouched) — but it is a real, load-bearing follow-on decision this design currently omits rather than a detail safe to leave unplanned for the implementation change. See the matching note added to Risks/Trade-offs below.

**Alternative considered:** concurrent consumption from all attached entries with a per-key version guard added to `KvProjection.applyEvent`/`advancePosition` (comparing the incoming `eventId` against a stored high-water mark before writing). Rejected for *this* change, not permanently — it is real, general hardening that would let concurrent multi-source consumption become safe unconditionally, but it touches `KvProjection`'s core write path (shared by `OneDbRouter`'s single-source case too, where it's currently unnecessary), is a bigger surface to review/test, and isn't needed to make a standalone KV-node process correct. Left as a documented future hardening step, not a requirement of this design.

**kv-node correction:** The failover mechanism closes the *specific* scenario Decision 6 in `add-kv-node-topology/design.md` described (two independently-ordered *connections* redelivering the same segments out of relative order with each other), but it does not close the deeper gap that scenario sits on top of, and the framing above ("closes the gap") overstates what it actually closes. Traced directly: a `WireSegmentCommittedSource` subscribing to `Event.SEGMENT_COMMITTED` on an entry (`client.subscribe(Event.SEGMENT_COMMITTED, ...)` after `login({realm: INTRA_REALM_NAME})`) attaches to the *exact same* fan-in point `NetEngineMill` already uses for live WAMP dispatch — `NetEngineMill`'s constructor does `this.sysApi.subscribe(Event.SEGMENT_COMMITTED, (body) => this.dispatchLiveEvents(body))` on that same entry's own `sys` realm (`lib/masterfree/netengine.ts`). That realm receives independent `Event.SEGMENT_COMMITTED` publishes piped in from every attached storage node (`EventStorageTask.listenEntry`'s `await this.api.pipe(client, Event.SEGMENT_COMMITTED, {exclude_me: false})`) — one per shard-owning storage node — with no merge/ordering step between them. This exact gap is independently traced end-to-end for the WAMP live-subscriber path in the sibling planning change `openspec/changes/live-dispatch-eventid-ordering/design.md`, which concludes "at no point ... does anything compare an incoming event's `eventId` against what has already been delivered" and confirms it is reachable specifically because "a moderately active realm will have events committing across many shards concurrently, each on its own storage node(s), each broadcasting independently" — exactly the traffic pattern this design's own Context section cites as the reason a KV-node needs the wire broadcast at all (a realm whose traffic spans multiple shards/storage nodes).

This means the ordering violation exists **even with exactly one active `WireSegmentCommittedSource` connection to exactly one entry** — it has nothing to do with how many entries a KV-node is attached to. Decision 3's active/standby discard rule only prevents a *second, differently-ordered connection* from re-injecting stale data; it does nothing about the single active connection itself delivering shard B's older `eventId` after shard A's newer one, which `ProjectionListener.handleSegmentCommitted`/`KvProjection.advancePosition` will apply exactly as received (still no per-key high-water-mark guard, per `add-kv-node-topology/design.md`'s own Decision 6 correction). So the Goals/Non-Goals section's claim ("Close the multi-entry-attachment safety gap... with a concrete failover design") and this Decision's opening framing are both narrower in effect than the gap Decision 6 actually flagged: failover removes the multi-*connection*-redelivery variant, but leaves the cross-*shard*-interleaving variant exactly as open as it was before this change — and unlike the multi-connection variant, this one is not unique to a standalone KV-node process at all; `OneDbRouter`'s own `dbFactory`-fed `ProjectionListener` is immune only because it is fed a single node's own local, already-ordered `EventStorageTask.commit_segment` stream, never a multi-storage-node wire broadcast — but that is exactly the coverage gap this whole proposal exists to fix (see Context bullet 1), so a real KV-node cannot inherit that immunity. Recommend either (a) narrowing this design's claim to "failover closes the multi-connection redelivery variant of Decision 6's gap; the cross-shard interleaving variant is tracked separately in `live-dispatch-eventid-ordering` and is not yet fixed for *any* `SEGMENT_COMMITTED` consumer, live-dispatch or KV projection alike", or (b) revisiting the per-key version-guard Non-Goal, since without it a KV-node's projections inherit the same unresolved ordering bug WAMP live subscribers currently have. Left for `kv-node`'s implementation change to decide; the current text should not be read as having fully closed Decision 6's gap.

A smaller, related observation from the same trace: the "exactly one `handleSegmentCommitted` in flight at a time by construction (JS single-threaded event loop...)" claim above is not quite accurate as stated, even for a single active connection. `HyperNetClient`'s decoder emits each decoded wire message synchronously (`decoder.on('data', msg => formater.onMessage(msg))` inside `socket.on('data', chunk => decoder.decode(chunk))`, `lib/hyper/net_transport.ts`), and `ProjectionListener`'s constructor invokes `this.handleSegmentCommitted(event).catch(...)` without awaiting it. If two `SEGMENT_COMMITTED` messages arrive in the same TCP read (plausible under load, or simply two shards committing close together), both `handleSegmentCommitted` calls start before either's first `await` resolves and can overlap. This doesn't change the recommendation above — it's a pre-existing characteristic of `ProjectionListener`, identical today in `OneDbRouter`/`ndb.ts` via `dbFactory.emit` — but "no additional locking is needed beyond `withWriteLock`" should be read as "no additional locking has been needed *so far*, for the same reason it hasn't been needed elsewhere today" rather than a guarantee this design newly establishes.

### 4. Registration gating: node-ownership check plus a local wildcard-precedence check, no new RPC

Two checks compose at `KV_ADD`/`SCHEMA_ADD` time, both implementable inside `admin_api.ts`'s existing handlers plus the already-built `Config.nodeOwnsRealmAndUri`:

1. **Ownership gate** (already specified by `add-kv-node-topology`, not yet enforced in code): reject unless `config.nodeOwnsRealmAndUri(myNodeId, realm, uriParts)`.
2. **Wildcard first-registration precedence** (new in this design): if this node's *only* covering pattern(s) for `realm` are wildcard-realm (`*`) patterns, and no projection is yet registered for `realm` on this node (a `StorageRegistry.list()` filter, or equivalently "this would be the realm's first-ever registration through this admin surface"), scan `config.getDbNodes()` for any *other* node id whose `storage` patterns include an exact-realm (non-`*`) match for `realm`. If found, reject with an error naming that node id/host/port as the expected target. If none is found anywhere in the config, accept — wildcard is genuinely the only coverage that exists or will ever exist for this realm under the current config, so deferring further would just be permanent unavailability.

This is entirely local: `Config` is loaded in full by every process from the same file, so "does some other node own this realm exactly" requires no cluster RPC, no coordinator, and no new admin event. It directly implements `add-kv-node-topology/design.md`'s resolved Open Question ("a realm's first `KV_ADD`/`SCHEMA_ADD` registration should require targeting a specific KV-node by id ... rather than relying on wildcard routing") as an enforced rule instead of an operational convention operators could silently violate.

**Alternative considered:** enforce this only as documentation/operator discipline (foxctl help text telling operators to target a specific node), with no code check. Rejected — the whole point of the prior change's resolution was that nothing today prompts a wildcard-only node to *not* accept a first registration it technically covers; a silent operator mistake (targeting the wrong, wildcard-only node first) is exactly the failure mode worth a cheap, local, always-on check for.

**kv-node verification:** Confirmed implementable against the real code, with one sharpening needed. `Config.getDbNodes()` (`lib/masterfree/config.ts`) returns the raw `{ [nodeId]: { host, port, storage: string[] } }` map, and `parseStoragePattern`/`nodeOwnsRealmAndUri` are already exported/usable for scanning other nodes' `storage` arrays — the check really is purely local, no new `Config` method required. `StorageRegistry` and `SchemaRepository` are both already realm-scoped by construction (`new StorageRegistry(db, realmName, makeId)`/`new SchemaRepository(db, realmName, makeId)` derive their table name from `realmName` in the constructor), so "does this realm already have a registration on this node" really is as cheap as the design assumes: `(await registry.list()).length === 0` (or `(await schemaRepo.list()).length === 0`), no new query shape needed.

One thing worth being explicit about, since `KV_ADD` and `SCHEMA_ADD` write to two different tables (`storage_desc_${realm}` vs `message_schemas_${realm}`): "no projection is yet registered for realm" is not one shared check across both handlers, it's two separate ones. `SCHEMA_ADD`'s first-registration check should look at `SchemaRepository.list()` — a schema is normally registered *before* any `KV_ADD` referencing it, since `admin_api.ts`'s own `KV_ADD` handler requires an existing `schemaId` (`this.schemaRepo.get(schemaId)`, throwing if not found) — while `KV_ADD`'s should look at `StorageRegistry.list()` as the design text already implies. Both are cheap and already-scoped; naming the right registry per handler avoids `kv-node`'s implementation change accidentally sharing one check between them (e.g. a realm with one registered schema but zero activated `KV_ADD` projections yet would wrongly look like "no registration yet" to a `StorageRegistry`-only check applied to `SCHEMA_ADD`).

Also confirmed Task 3.3's constructor change is clean, not just assumed so: `AdminApiServer`'s constructor today is exactly `(realm: BaseRealm, realmName: string, db: sqlite.Database, projectionListener: ProjectionListener, makeId: ProduceId)` — five required positional parameters, no existing optional trailing one — and `OneDbRouter.initRealm` calls it with exactly those five, in that order, with no other call site anywhere in the codebase. Appending `myNodeId?: string` as a sixth, optional, trailing parameter is backward compatible: `OneDbRouter`'s existing five-argument call site continues to compile and receive `undefined` for it, exactly as `tasks.md` 3.3 assumes — no wrapper, no overload, no change to `OneDbRouter` needed.

### 5. `KV_NODE_LIST` lives on every KV-node's own admin gate

Registered in `admin_api.ts` next to `EVENT_SHARD_LIST`, using the same `config.getDbNodes()`-flattened-to-rows shape sketched (not built) by `add-kv-node-topology/design.md`:

```
AdminEvent.KV_NODE_LIST = 'fox.admin.kvnode.list'
AdminDbNodeEntry = { nodeId: string; host: string; port: string; pattern: string }
AdminKvNodeListResponse = { nodes: AdminDbNodeEntry[] }
```

**Why a KV-node's own gate, not a cluster coordinator:** there is no cluster coordinator process in this architecture at all — entry, sync, and storage nodes are each symmetric peers within their own tier, with no elected or designated leader (consistent with the stateless-voting invariants). Inventing one just to serve a read-only config listing would be new architecture for no behavioral gain.

**Why not `foxctl` computing it client-side from config alone:** `foxctl` is an operator CLI that may run from a machine without the cluster's `supervisor/config.json` available (e.g. a laptop, CI, or a bastion host), and it already has zero other config-file-reading code paths — every other `foxctl` command works by dialing a live node and calling an RPC. Serving it live also incidentally confirms the responding KV-node is up and actually running with that config (config drift between what's on disk and what a live process loaded becomes visible), which a purely offline client-side computation cannot.

Any KV-node can answer this identically regardless of which node's `storage` patterns cover what, since it's `config.getDbNodes()` flattened without any node-ownership filtering applied (mirroring `EVENT_SHARD_LIST`'s no-filtering, return-everything style) — a `foxctl kvnode list` call can be pointed at *any* running KV-node.

### 6. Catch-up: pull realm history over the existing per-shard `historyFetchTopic` RPC, not `ProjectionListener`'s local-db backfill

`event-history-node`'s review (see the corrections under Decision 3 and its matching Risks bullet above) found that `ProjectionListener._runActivation`'s backfill is a silent no-op for a standalone KV-node: it only replays history `if (activationTarget)`, and `activationTarget` comes from `StorageRegistry`'s `latestRealmEventId(db, realmName)`, which queries `event_history_${realmName}` — a table only `EventStorageTask`/`DbEngine` ever create and populate. A KV-node's own local db, as scoped by this design, never has that table (it stores projections, not raw event history — a deliberate, smaller disk footprint worth keeping, not a gap to close by replicating full history locally). Left unaddressed, this silently breaks two things, not one: a projection's *first* activation (treated as "activating an empty realm," per `kv-storage-registry`'s existing spec scenario, even when the realm has extensive history) and recovery of any gap left by an entry connection outage (Decision 3's own failover-promotion path, plus a storage-node-side reconnect to an entry, which `pipe()` — confirmed by `event-history-node` to be a plain live subscribe-and-republish with no queue or replay — silently drops for the outage's duration).

**Decision:** reuse the existing per-shard catch-up primitive the entry node already relies on for its own subscribers — `EventStorageTask.announceToEntry` (`storage.ts`) already registers `Event.historyFetchTopic(shard)` as an RPC directly on every entry it attaches to, for every shard it owns; that registration lands on the entry's own realm object, reachable by *any* session logged into that entry (confirmed by `kv-node`'s trace of `register()`'s remote-realm binding in Decision 1's verification) — not just the entry's own internal `SharedSegmentBuffer` (`lib/masterfree/net_sub.ts`), which already implements exactly this fetch-and-merge pattern for the entry-side "retained + after" synchronized-subscription feature. A KV-node's own outbound connection to an entry qualifies as such a session. Concretely, the KV-node's activation/catch-up flow:

1. Calls `client.callrpc(Event.historyFetchTopic(shardTag), { realm, afterEventId: record.currentPosition }, { progress: appendBatch })` against its currently-*active* entry connection, for every `shardTag` in `[0, TOTAL_SHARDS_COUNT)` — the same call shape `SharedSegmentBuffer.ensureLoading` already uses, including its existing handling of a shard with no owning storage node attached (`ERROR_NO_SUCH_PROCEDURE` treated as "nothing to fetch from this shard," not an error).
2. Merges the returned batches into ascending `eventId` string order (the same de-dup/insertion-order logic `SharedSegmentBuffer.appendEvents` already implements — reusable as-is or duplicated narrowly, an implementation-change decision, not a design one).
3. Applies each merged event through a `KvProjection` instance's `applyEvent`, then `advancePosition`, strictly in that merged order — while the projection's registry status is `refreshing` (so `ProjectionListener.handleSegmentCommitted`'s existing `status === Online` filter already excludes it from the live wire-tail path for the duration, with no extra coordination needed — matches `kv-storage-registry`'s existing "Rejecting duplicate activation" status-machine, just driven by a different data source than local history).
4. Once every shard's RPC call has resolved (a natural, bounded termination — `handleHistoryFetch` is a snapshot read of history *as of the call*, not an open-ended live stream), transitions the projection to `online` — matching the existing "Transitioning to online" requirement's observable contract exactly, just reached via a wire pull instead of a local SQL scan.

This requires a small, targeted seam — not the sweeping `ProjectionListener` rewrite the original Non-Goals draft foreclosed. The cleanest shape (left for the implementation change to pin down exactly) is a small pluggable interface, e.g. `RealmHistorySource { fetchSince(realm, afterEventId): AsyncIterable<HistoryEvent> }`, with two implementations: today's local-db read (`LocalDbHistorySource`, wrapping `History.getEventHistory`, used unchanged by `OneDbRouter`/`ndb.ts`-colocated `ProjectionListener` instances) and a new `WireHistoryFetchSource` (wrapping the per-shard RPC pull above, used only by a standalone KV-node's `ProjectionListener`/activation path). `ProjectionListener`'s constructor takes this source alongside its existing `SegmentCommittedSource`; `_runActivation` calls it instead of `getEventHistory` directly. This is additive to `ProjectionListener`/`StorageRegistry` (a new constructor parameter and an internal indirection), not a change to their existing observable behavior for `OneDbRouter`/`ndb.ts` callers, who keep getting `LocalDbHistorySource` and see no behavior change.

**Alternative considered:** have the KV-node's admin RPC handler bypass `ProjectionListener.startActivation`/`_runActivation` entirely and implement its own parallel activation flow directly against `StorageRegistry`/`KvProjection`. Rejected — it would duplicate `_runActivation`'s status-transition bookkeeping (`refreshing`→`online`/`failed`, `last_error`, the "retrying after failure starts from `current_position`" behavior) that has nothing to do with *where* history comes from and already works correctly regardless of node type; a pluggable source is a smaller, more targeted change than a second activation implementation.

### 7. Cross-shard `eventId` ordering at the `SEGMENT_COMMITTED` fan-in point: an acknowledged, scoped, shared risk — not re-solved here

`kv-node`'s review found that Decision 3's active/standby failover closes only the *multi-connection redelivery* variant of the monotonicity risk — it does not close a deeper, pre-existing one: a `WireSegmentCommittedSource` subscribes at the exact same fan-in point `NetEngineMill.dispatchLiveEvents` already uses for live WAMP dispatch on an entry node, and that fan-in point multiplexes independent per-shard broadcasts from multiple storage nodes with **no merge/ordering step across shards** — already traced in detail (for the WAMP-subscriber case) by the sibling planning change `openspec/changes/live-dispatch-eventid-ordering/`. This means cross-shard `eventId` mis-ordering can reach `ProjectionListener.handleSegmentCommitted`/`KvProjection.advancePosition` even with exactly **one** active KV-node-to-entry connection — it is not a failover/multi-connection problem, so Decision 3 cannot be extended to cover it.

**Decision:** treat this explicitly as a shared dependency on `live-dispatch-eventid-ordering`, not as something this change re-solves, with a concrete interim stance so the KV-node implementation isn't blocked on that sibling change landing first:

- **If `live-dispatch-eventid-ordering` lands first** (its k-way merge across per-shard sorted streams, applied at `NetEngineMill.dispatchLiveEvents`): `Event.SEGMENT_COMMITTED`'s live-tail delivery is already correctly ordered by the time `WireSegmentCommittedSource` consumes it, and this design needs no further change.
- **If the KV-node implementation lands first** (or the two proceed independently): `WireSegmentCommittedSource` SHALL keep a small, strictly-bounded per-realm high-water-mark (one `eventId` string per realm it has ever seen, not per-`advanceId` and not per-event — bounded by realm count, consistent with the "no unbounded per-advanceId state" invariant this design must not violate even though a KV-node sits outside the StageOne/StageTwo voting path itself) and SHALL drop — not reorder-buffer, to avoid the unbounded heap growth a reordering queue would require — any incoming record whose `eventId` does not exceed that realm's current high-water mark, logging a warning. This is a lossy, heap-bounded, monotonicity-safe interim guard: strictly worse than the real k-way merge (it discards rather than correctly reorders a genuinely-late-but-valid record), but it prevents `advancePosition`/`KvProjection` from ever regressing, which is the correctness property this design must guarantee. It is documented as an interim measure to be removed once `live-dispatch-eventid-ordering` ships, not a permanent feature.

**Alternative considered:** block this change on `live-dispatch-eventid-ordering` landing first. Rejected — the two changes have different owners and different urgency; making a standalone KV-node process available even with a documented, bounded, interim ordering guard is more valuable than gating it on an unrelated cluster-wide fan-in fix, especially since the guard above is small, local to `WireSegmentCommittedSource`, and does not touch any shared write path (`KvProjection`, `ProjectionListener`'s live-tail logic) that `live-dispatch-eventid-ordering`'s eventual fix will also touch.

## Risks / Trade-offs

- **[Risk]** A KV-node whose outbound entry connections all drop (e.g. every configured entry node is down) stops receiving `SEGMENT_COMMITTED` entirely, silently going stale while continuing to serve reads/admin RPCs against increasingly outdated projections → **Mitigation**: out of scope for this design to solve fully (no new staleness-alerting mechanism proposed), but `storage_desc_${realmName}.current_position` already gives an observable staleness signal any monitoring can poll via `KV_LIST`; flagged as a follow-on for `kv-node`'s implementation change to consider exposing more directly (e.g. a last-applied-timestamp field), not solved here.
- **[Trade-off]** Discarding (not queuing) standby deliveries during normal operation means a KV-node's freshness is bounded by its *active* connection's health only — a standby being slightly ahead of the active connection (e.g. a network partition that isolates the active connection from part of the entry-node's own upstream while the standby's path is fine) does not help until failover actually happens. Accepted: correctness (no regression) is prioritized over minimizing staleness windows, consistent with Decision 3's rationale, and `ProjectionListener`'s existing catch-up/activation path already bounds the actual cost of a gap. **event-history-node correction:** that last clause is not accurate for this node type — see Decision 3's correction above. `ProjectionListener`'s local-history backfill (`_runActivation` → `latestRealmEventId`) is a silent no-op on a KV-node, since `event_history_<realm>` is never populated there, so this staleness window is *not* bounded by existing catch-up machinery as originally framed here; it is currently unbounded (permanent, not "a brief pause") until a pull-based catch-up over the existing per-shard `Event.historyFetchTopic` RPC (already used by `lib/masterfree/net_sub.ts`) is designed for the KV-node's activation and failover-promotion paths. That design work is not done in this document and should not be treated as already covered.
- **[Risk]** The wildcard first-registration precedence check (Decision 4) only fires for a realm's literal first registration on a given node; if an operator later reconfigures `dbNodes` to remove the previously-exact-match node's pattern for a realm, existing wildcard-covering nodes are not retroactively re-checked. → **Mitigation**: this is the same class of cross-node coverage-gap problem `add-kv-node-topology/design.md`'s Risks section already deferred to `foxctl`/operator tooling as a live reconciliation concern; this design does not re-solve it, only prevents the *initial* mistake.
- **[Risk]** Decision 6's `WireHistoryFetchSource` pull re-fetches a realm's full matching history from `afterEventId` forward on every activation/retry, with no cap on how much a very long-lived, high-volume realm's backlog could be — potentially a slow activation for an old, busy realm's first-ever KV-node registration. → **Mitigation**: this is the same bounded-snapshot cost `SharedSegmentBuffer`/the "retained + after" synchronized-subscription feature already accepts today for exactly this kind of catch-up; not a new class of cost introduced by this design, and out of scope to optimize (e.g. via segment-level bulk transfer) beyond what already exists.
- **[Trade-off]** Decision 7's interim per-realm high-water-mark guard is lossy by design (drops rather than reorders a late-but-valid record), so a KV-node running before `live-dispatch-eventid-ordering` lands can silently skip a legitimately-late event's projection update rather than eventually applying it correctly. Accepted: the alternative (an unbounded reorder buffer) would violate the same heap-boundedness expectation the rest of this architecture holds StageOne/StageTwo to, and the guard is explicitly interim, removed once the sibling change ships.

## Migration Plan

Purely additive at the process-topology level: a new process type that isn't started unless an operator adds it to their deployment scripts (`supervisor/config.json`'s `dbNodes` section is already checked in but nothing currently launches a `kvnode.ts` process against it). No existing entry/sync/ndb/OneDbRouter code path is touched by this design beyond `admin_api.ts` gaining new gate logic and RPC handlers (additive registrations, no existing handler's behavior changes) and `hyper.h.ts` gaining new additive types. Rollback is simply not running the new process; nothing else in the cluster depends on its presence.

**event-history-node verification:** Confirmed no change to `storage.ts`'s `SEGMENT_COMMITTED` publish/pipe path is needed to support N KV-nodes each attached to M entries. `this.api.publish(Event.SEGMENT_COMMITTED, result, { exclude_me: false })` (line 118) and the `pipe()` it rides on (`lib/hyper/client.ts`, `pipe()` is just `subscribe(topic, cb)` that republishes) both terminate in `BaseRealm.disperseToSubs()` (`lib/realm.ts`), which iterates `this.matchTrace(event.uri)` with no cap on subscriber count and no per-subscriber bookkeeping in `storage.ts` itself — fan-out to any number of attached entries, and from each entry's own realm to any number of further-attached KV-nodes, is already unbounded/generic pub-sub, not something `EventStorageTask` assumes a fixed or known count for. No backpressure mechanism exists at this layer for *any* number of consumers today (one or many) — `publish()` doesn't wait on slow subscribers — so multiple KV-node consumers change nothing structurally here; whatever backpressure behavior exists (or doesn't) is unchanged by this design. This is separate from, and does not mitigate, the backfill/catch-up gap identified as an `event-history-node correction` under Decision 3 above.

Sequencing with `add-kv-node-topology`: this change's `distributed-mode` delta is additive to that change's still-unarchived delta (different requirement names, no overlap) but conceptually depends on it — recommend archiving `add-kv-node-topology` at or before archiving this change, so `distributed-mode.md`'s final text reads as one coherent narrative (KV-node as fourth node type, then this change's process-level detail) rather than needing manual reconciliation.

The two questions raised during this change's own `kv-node`/`event-history-node` review — the catch-up/backfill gap and cross-shard ordering exposure — are resolved above as Decisions 6 and 7 respectively, each with a concrete mechanism and explicit sequencing/removal conditions, rather than left open.
